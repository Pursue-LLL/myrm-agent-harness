# core/security/detection/

## Overview
Security detection modules — PII classification, content boundary marking, information leak detection, prompt injection guard, intent router, pseudonymization, and semantic element risk classification.

## File & Submodule Index

| File | Role | Description | I/O/P |
|------|------|-------------|-------|
| __init__.py | Package | Module public exports for core security detection subsystem. | — |
| content_boundary.py | Core | Content boundary marking — wraps untrusted/tool output with Nonce-guarded delimiters and privileged tag stripping; `extract_wrapped_payload` unwraps envelopes via symmetric pairing for programmatic (PTC) consumers. | ✅ |
| custom_rules.py | Core | Custom keyword and pattern rules (SSOT for where a user-defined term sits in a text) — `custom_rules(policy, *levels)` lists the keywords and patterns a `PrivacyPolicy` has for those levels (blank entries dropped, since an empty keyword would match everywhere); `find_custom_spans` returns every non-overlapping span (leftmost, longest first) and `first_custom_span` the first hit in rule order; `ineffective_patterns` names the patterns that cannot be used (they do not compile or are too large to build) and `pattern_problem` says why one cannot (the engine's message, or the repeats being too large), for a caller that compiles patterns itself and must pass this check first. A keyword matches in any case at every occurrence, and the space of a keyword of several words stands for any run of whitespace (a line break, a tab, a no-break space: a pasted text wraps lines); an edge character of a script written with spaces (ASCII letters and digits, underscore, Latin, Greek, Cyrillic) needs a word boundary (`pin` is not in `spinners`, `pass` is not in `password123`), an edge that is Chinese, Japanese, Korean or punctuation needs none (`凤凰计划` matches inside a sentence, `project` between Chinese characters, `.env` only needs a closed tail). A pattern is a case-insensitive regular expression in the `regex` package's syntax (everything `re` accepts, plus Unicode property classes such as the Han script class, and `(?<name>...)` groups); one that does not compile, is nested too deep or has counted repeats that add more than `_MAX_REPEAT_ATOMS` atoms to what it spells out (the engine builds every copy when it compiles: `a{99999999}` would take gigabytes, `(?:a{1000}){1000}` ~300 MB; the length of a pattern is not limited by this) never matches, and a zero-length match is no span. A pattern that cannot finish a text within the time budget (`_PATTERN_TIMEOUT_SECONDS`; a backtracking blow-up would otherwise keep a worker and a CPU core busy for minutes) counts the whole text as its hit (`CustomSpan.timed_out`, kept even where it touches a marker, the remaining rules are skipped), so the text is masked instead of let through. A span touching a marker an earlier redaction or pseudonymization wrote (`[PII:phone]`, `[REDACTED:key]`, `<PHONE_NUMBER_1>`) is dropped, so applying the rules to their own output changes nothing. Consumed by `pii_classifier`, `pii_redactor` and `pseudonymizer`, so a term that is detected is a term that is masked. Known limits: keywords are matched literally (no stemming or synonyms); a pattern that sits near the time budget on a long text can hit it on one turn and not on the next, and masks the whole text on the turns it does. | ✅ |
| entropy_scan.py | Core | Unknown-credential tier of the leak detector — `scan_high_entropy` returns random-looking tokens from free text (URLs, UUIDs, long hex digests and file paths are removed first; a token must be at least 24 ASCII characters with letters and digits, not a hex or base64 blob, not a reference to a secret per `secret_value.is_reference_token`, and at or above 4.2 bits of Shannon entropy per character); `shannon_entropy`. Consumed by `leak_detector`. | ✅ |
| instruction_shape.py | Core | Instruction-shape detector — sentence-level agent-directed shapes (guardrail bypass, unattended execution, exfiltration, spoofed approval, agent command, untrusted-channel-write) in durable content. | ✅ |
| intent_router.py | Core | Intake-stage dangerous intent router — dual-tier regex & actionability detection for mass destruction, mass exfiltration, and privilege mutation. | ✅ |
| leak_detector.py | Core | Information leak detector — identifies sensitive data patterns in text (vendor prefixes, ENV/JSON/Header context, structural formats, entropy, mnemonic seeds); earlier redactions (`[REDACTED:*]` markers, the PII redactor's `[REDACTED] [PII:password]`, `abcdef***...wxyz` partial masks) count as placeholders, so redacted text scans clean. ENV-credential values, JSON-credential values and entropy tokens that are references to a secret (`secret_value`: call arguments, attribute chains, templates, class names, slugs, addresses, query strings) are neither flagged nor redacted. ENV assignments and JSON fields share one value rule (`_credential_value`: at least 16 characters, not a placeholder, not a reference); a JSON key may carry a prefix before the credential word (`SecretAccessKey`, `SessionToken`, `aws_secret_access_key`, `db_password`, `x-api-key`), and the value is redacted by position so a key containing the value's text stays intact. Under a prefixed key a value counts only as a single ASCII token that is not a paging handle, because such keys also name UI strings (`"setupToken": "Add GITHUB_TOKEN to the server settings"`, Chinese or Korean text) and continuation tokens the caller passes back verbatim (`NextContinuationToken`, `nextToken`, `next_token`, `nextSyncToken`: a bare `...Token` key whose last prefix word is a paging word — next, prev, page, continuation, cursor, sync, resume, start; `nextAuthToken`, `pageAccessToken` and `cursorApiKey` stay credentials); under a bare key (`token`, `passphrase`) a spaced value (`Bearer <token>`) still counts. The entropy tier lives in `entropy_scan.py`. `DISTINCTIVE_KEY_PATTERNS` is the part of the vendor-prefix table where the prefix identifies a key on its own, for a caller that must refuse a message and so must not match a name: a short prefix that also begins identifiers (`vercel_`, `fal_`, `telegram_bot`) is left out, and a new shape is exposed unless it is added to the weak list; a caller joins the patterns into one alternation, so each is flag-free and has no group and carries no boundary of its own. A vendor prefix counts as a key only where a token starts (`token_start.py`: not right after an ASCII letter or digit, but a JSON-escaped tab or line break and a percent-encoded byte such as `%3D` separate; `telegram_bot`, which opens with digits, only rules out a longer number in front): `sk-` also ends "task", "risk" and "disk", so a long hyphenated URL slug is neither flagged nor masked, while a key after punctuation, an underscore, a quote, an escaped line break or CJK text still is; a key written directly after a letter or digit (`mykeysk-...`) is detected by no tier. Known limits: a value shorter than 16 characters under an ENV/JSON key is not redacted here (durable writes also run the persistence scan's assignment tier); a spaced or non-ASCII value under a prefixed key is not recognised; JSON embedded in a string with escaped quotes (`{\"key\": \"value\"}`) is not matched; credentials in absolute-URL query strings or userinfo, `curl -u` pairs and cookies carry no ENV/JSON label and absolute URLs are excluded from the entropy tier, so they are not detected here. | ✅ |
| token_start.py | Core | Left-boundary wrapper for the vendor-prefix shapes — `TOKEN_START` (not after an ASCII letter or digit; a JSON-escaped tab or line break and a percent-encoded byte count as separators) and `NUMBER_START` (not after a digit, for a shape that opens with digits) are the boundary as a regex fragment, which a caller that joins shapes into one pattern puts in front; `TokenStartPattern(pattern, start)` offers `search` / `finditer` / `sub` over the matches of the pattern that follow the start, checking the boundary on each match and resuming one character after a rejected one, because a lookbehind at the front of the pattern makes the regex engine try every position instead of skipping to the literal prefix (about ten times slower on ordinary text). The pattern must not match the empty string. | ✅ |
| password_heuristic.py | Core | Keyword-anchored password heuristic for secrets the leak detector misses — `find_password_spans` returns the secret's own span per keyword occurrence: a value the text introduces (`is`/`to`/`:`/`=`/`是`, judged by `secret_value_span`) else a generated-looking token nearby (4 classes among lower/upper/digit/strong symbol, within a tight window; the keyword, neighbouring capitalised words and references such as `status.HTTP_400_BAD_REQUEST` or `a-zA-Z0-9_` never win), plus numeric PIN/OTP/2FA codes anchored to keywords (a code after the keyword within a tight window, or one before it in the same clause; `#1234` issue references and years/mobile numbers never count; "pin" counts only as the acronym `PIN`, when introduced (`is`/`:`/`是`) or when the code follows it directly, since it is also a verb). Text without a keyword yields nothing. A label may end in the keyword (`DB_PASSWORD`) but not continue it (`passwords`, `password_hash`), and the redactor's own `[PII:password]` tag is never a label; a value stops at a quote, comma or semicolon. One definition serves two callers: `strict=True` (default, text that is stored: eight characters with a digit or symbol) and `strict=False` (text that leaves the machine, used by `pii_classifier`, `pii_redactor` and `pseudonymizer`: a value assigned with `:`/`=`/`：` counts from six characters, letters-only or numeric, so `password: 123456` is a password while `password is hunter2` and references stay out). `find_keyword_password_spans` is the keyword branch alone, without the numeric codes, for a caller that must not act on a short-lived code (`find_password_spans` is that branch plus the codes); `PASSWORD_KEYWORD_RE` is the keyword set, public as the cheap test of whether a text can hold a password at all. | ✅ |
| secret_value.py | Core | Secret value rules (SSOT for "secret or reference to one"). `secret_value_span` trims a raw labeled or connector value span and accepts it only when plausible (length, not numeric/field-state/mask, no code-expression brackets, no URL; `allow_letters_only` and `allow_numeric` let a caller that knows the label names a password accept `dragonfly` or `123456`, and repeated digits are a password while repeated symbols are a mask), not a bare name (constant, snake-case, unquoted camel-case) and not a reference. `is_reference_value` is the shared reference test: templates (`$X`, `${X}`, `%(x)s`, `{x}`, `<x>`), attribute chains whose parts are digit-free identifier-sized runs or digit-bearing constants (a `hex32.alnum16` credential or `john.Smith2024` is not one), such a chain of three or more parts with a trailing TypeScript non-null `!` (`process.env.GROQ_API_KEY!`; after two parts `john.smith!` is as likely a password), calls on compound names, regex fragments (adjacent ranges such as `a-zA-Z0-9_`, a quantified `\s+`), the label itself (`password=password`) and bare names given as call arguments; `$` and `%` inside a value stay password characters. `is_reference_token` is the entropy-scan counterpart: a token is a reference when every piece between non-alphanumeric characters is readable (short words in lower/Capitalised/ACRONYM form with trailing digits, a number, a letter, a version tag), so identifiers, class names, constants, slugs, domains and query strings pass while one random piece (a secret behind `?token=` or `@`, a `<alnum20>.<alnum20>` credential) keeps the token a candidate; keyword-argument values are judged alone. Also `mask_markdown_emphasis`, `Span` and the symbol vocabulary. Consumed by `password_heuristic`, `persistence/secret_spans`, `leak_detector` and `entropy_scan`. Known limits: a password containing `()[]{}<>` is not recognised by the labeled-value tier (a `KEY=value` of at least 16 characters is still caught by `leak_detector`), and a letters-only unquoted camel-case value after a password key reads as a name. | ✅ |
| iban.py | Core | IBAN detector — `IBAN_LENGTHS` (the SWIFT registry's 89 countries and the length each IBAN has), `IBAN_RE` (country code, two check digits and the account part in one run or in groups of four with an optional short last group, either case; built per length so a match ends exactly where its IBAN does and a word that follows is never swallowed), `iban_valid` (known country, exact length, mod-97 remainder 1; one random look-alike in 97 survives it) and `inside_iban(text, start, end)` (whether a span lies within a valid IBAN, looking only at the stretch before it where such an IBAN could begin, so the cost does not grow with the text). Read through `pii_patterns` by the classifier, the redactor and the pseudonymizer. Known limit: an IBAN typed with hyphens or other separators is not matched. | ✅ |
| card_context.py | Core | Keyword-anchored card-number detector — `find_card_number_spans` returns the span of a card number (13-19 digits, or typed 4-4-4-4 / 4-6-5 / 4-6-4 with one hyphen or space) that follows a card keyword (`银行卡`, `信用卡`, `储蓄卡`, `借记卡`, `卡号`, `bank card`, `credit card`, `debit card`, `card number`, `card no`) within sixteen non-digit characters on the same line; the number only, never the keyword or the expiry date and CVV after it. A bare `card` is not a keyword (SIM card, member card), nor is a word that merely ends in one (`discard number`). It covers what the prefix table in `pii_classifier` cannot: networks outside the table (Maestro, Mir, RuPay, Troy) and numbers with a typo (they fail the Luhn check). `find_card_number_spans` is consumed by `pii_classifier`, `pii_redactor` and `pseudonymizer`, so a card that is detected is a card that is masked. `CARD_CONTEXT_RE` is the keyword-and-number pattern itself (case-insensitive, the number in the `number` group), read by the server's built-in risk rule for bank cards so the gate and the classifier agree on what a card is. | ✅ |
| pii_patterns.py | Core | PII pattern tables and validators (SSOT for what the built-in regex detectors look for; passwords, credentials and keyword-anchored cards are found by span in `password_heuristic`, `leak_detector` and `card_context`) — `S3_PATTERNS` (`china_id_card`, `bank_card`, `china_passport`) and `S2_PATTERNS` (`iban`, `china_phone`, `intl_phone`, `us_phone`, `email`, `credit_card_visible`, `private_ip`, `china_address`, `china_courier`, `us_ssn`) as (name, pattern) tables, the individual patterns the redactor pairs with its masks, the checksums `luhn_valid` / `bank_card_valid` / `china_id_valid` (decimal digits only; anything else fails instead of raising), `is_confirmed(name, match)` (the one place that says which match is a real hit: it survives the checksum its type calls for, and a card number that lies within a valid IBAN is a run of the account number, not a card; read by the classifier, the redactor and the pseudonymizer) and `is_placeholder`. A bank card (S3, Luhn-checked) is a number of a major network (Visa, Mastercard 51-55 and 2221-2720, UnionPay, Amex, JCB, Discover) as one run of 15-19 digits or typed with the same hyphen or space between the groups: four of four (`4532 0151 1283 0366`), UnionPay's fifth group of three (`6222 0212 3456 7890 011`), Amex as 4-6-5 (`3782 822463 10005`); an expiry date typed after the number is not part of it. A grouped number that fails the check stays a visible card (S2, `credit_card_visible`). An IBAN (S2, `iban`; it names an account but does not authorise a payment from it) is read from `iban.py` and tried first, because typed in groups its digits also look like a visible card. A mainland phone number is one run of 11 digits or typed as `138 0013 8000` / `138-0013-8000` (the typed form must not follow a letter, so the tail of a UUID is not read as a number). A US number written without the country code (`(415) 555-2671`, `415-555-2671`, optionally led by `1-`; area code and exchange do not start with 0 or 1) is `us_phone`; behind a `+<country code>` the international pattern reads the number, so no number is found by both. An email address is a local part of up to 64 characters and a domain of up to 255 (the RFC 5321 limits), which keeps the search linear on a long run of address characters; behind a longer local part only its last 64 characters are masked. Consumed by `pii_classifier`, `pii_redactor` and `pseudonymizer`, so a value that is detected is a value that is masked. Known limits: Diners Club, mixed separators, other separators (no-break space) and grouped ID card numbers are not matched. | ✅ |
| pii_classifier.py | Core | PII classifier — classifies a text as S1/S2/S3 and names the pattern that decided it (`classify_content`), running the built-in detectors of `pii_patterns` and `card_context`. A password is not a regex here: `classify_content` asks `password_heuristic.find_password_spans(strict=False)` (pattern name `password_context`); a number the text introduces as a card but the prefix table misses (other network, typo) is S3 under `bank_card_context` (`card_context`). The user's custom S3 keywords and patterns (`custom_rules`) are checked first and the custom S2 ones before the built-in S2 patterns, on a text of any length (pattern names `custom_s3_keyword:<keyword>`, `custom_s2_pattern:<first 50 characters>`); the built-in detectors skip texts shorter than six characters. `contains_level(content, policy, level)` says whether a text holds something of one level (a text that reaches S3 may hold S2 content too), by the same custom-then-built-in rule as `classify_content`. `classify_tool_params` checks every string parameter, short ones included. | ✅ |
| prompt_guard.py | Core | Prompt injection guard — 10 EN + 4 ZH injection categories with anti-obfuscation (leet speak, invisible Unicode, whitespace) and word-boundary precision. Two-tier score: `max_score` (every hit; audit trail and durable-store gates) vs `block_score` / `should_block` (only hits unambiguous on their own; consumed by the live-input guard and the rule-file loader, so plain role assignment like `Act as a translator` is audited but not blocked). Negated extraction verbs (`Never print the API keys`) are not reported. | ✅ |
| semantic_risk.py | Core | Semantic element risk lexicon (SSOT) — bilingual destructive/financial/account/admin/publish vocabulary classifying GUI controls (role + name) as high-risk; consumed by browser DOM and desktop AX interaction gates so all GUI channels share one identical gate vocabulary. | ✅ |
| harmful_state_detector.py | Core | Harmful psychological state detector — blocks self-harm/severe depression patterns from persistent memory storage. | ✅ |
| pseudonym_store.py | Core | Pseudonym store — persistent mapping between real values and pseudonyms. | ✅ |
| pseudonymizer.py | Core | Pseudonymizer — replaces PII with reversible pseudonyms using the pseudonym store. At S3 the password values found by `password_heuristic` are replaced, the label stays (`password: <PASSWORD_1>`). The user's custom keywords and patterns of the processed level (`custom_rules`) become `<CUSTOM_KEYWORD_n>` / `<CUSTOM_PATTERN_n>` tags after the built-in detectors; one tag per distinct original, so the restorer returns the original text of each occurrence. At S3 a card number introduced by a card keyword (`card_context`) becomes `<BANK_CARD_n>` too, unless the prefix table already replaced the same digits. An IBAN becomes `<IBAN_n>` at S2; an item that lies within another (the digit groups of a typed IBAN that also read as a visible card) is dropped, so it neither adds a pseudonym nor counts. | ✅ |
